I want to create a new **Project Documentation Module** inside my existing application.

The purpose of this module is to provide a complete, easy-to-understand guide to the entire application.

A new developer, client, tester, admin, or team member should be able to open this Documentation Module and understand:

* What the project does.
* How to access and sign in to the system.
* What every module does.
* How modules are connected.
* How data flows through the system.
* How candidates move through the recruitment process.
* How Job Applications work.
* How Forms work.
* How Interviews work.
* How Google Meet or meeting integrations work.
* How the Live Coding feature works.
* How candidate information is stored.
* How APIs and backend processes work.
* How database entities are connected.
* How external services such as Google Cloud are used.
* How to manually test each module.

The Documentation Module should be designed as an **interactive, professional, easy-to-navigate documentation center**.

IMPORTANT:

Before implementing anything, analyze the existing project architecture and all existing modules.

Do not guess.

Do not create documentation for functionality that does not actually exist.

First inspect the codebase and identify all real modules, integrations, routes, APIs, database entities, authentication flows, and external services.

Do not modify unrelated functionality.

# DOCUMENTATION DATA STRATEGY

Before implementing, determine the best approach for storing documentation.

Possible options:

1. Markdown files inside the project.
2. Structured JSON/content files.
3. Database-driven documentation.
4. A combination of static documentation and dynamic project data.

Choose the simplest maintainable solution that fits the existing project.

For the first version, prefer a structure that developers can easily update.

The documentation must not expose:

* API keys.
* Environment variables containing secrets.
* Passwords.
* Database credentials.
* Private tokens.
* Sensitive user information.

# FINAL IMPORTANT RULES

1. Analyze before implementing.
2. Do not guess how modules work.
3. Read the actual code.
4. Document only real functionality.
5. Clearly identify planned functionality separately.
6. Do not expose secrets or credentials.
7. Use one common documentation format for all modules.
8. Make the documentation understandable for both technical and non-technical users.
9. Reuse the existing application UI and architecture.
10. Do not break existing functionality.
11. Do not unnecessarily refactor unrelated modules.
12. Create clear flows showing how all modules connect.
13. Document actual Google Meet and cloud integrations accurately.
14. Include a complete manual testing guide for every module.

The final result should feel like a complete internal **Product Documentation + Technical Documentation + QA Testing Center** built directly inside the application.
