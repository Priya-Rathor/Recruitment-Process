*** BUILT. 2026-08-22. ***

This module has been implemented. The specification below is what it
was built from and still describes it accurately; the authoritative
record of what actually exists — files, reuse, security decisions,
manual test cases and the remaining gaps — is:

    docs/modules/23-forms-public-applications.md

Migration: supabase/migrations/0033_module23_forms_public_applications.sql

Deviations from this spec, all deliberate and explained in that doc:

  1. A DISABLED form and an UNKNOWN token show DIFFERENT messages.
     Section 9 below asked for one neutral page for both. Reaching the
     "no longer accepting applications" page requires a signature this
     server produced, which cannot be forged — so anybody who gets
     there was genuinely given the link, and telling them the role has
     closed is both true and kinder. A regenerated-away link is still
     treated as invalid, so an old QR code's holder is told to ask for
     the current link.
  2. FILE UPLOAD is only the resume, only on a job application form.
     The type is not offered as a custom question and is refused
     server-side elsewhere: nothing in this module stores an arbitrary
     attachment, so offering it would take somebody's document and drop
     it. Same call Module 19 made about its upload link.
  3. A STANDALONE FORM CANNOT YET BE ASSIGNED TO A CANDIDATE. Its
     answers are stored and readable, but the "send this questionnaire
     to this shortlisted person" step (Feature 13) is not built. The
     data model supports it — form_responses.candidate_id exists.
  4. NO CANDIDATE COLUMNS were added for current salary, LinkedIn,
     GitHub or portfolio, as section 6 required. Those answers live on
     the application's responses card.

Also fixed on the way through: activity_entity_type was missing
'message_template' and 'privacy', which had been declared in TypeScript
for some time — every audit row for those two entity types was being
silently dropped, including privacy-log entries.

1. CORRECTIONS TO THE EARLIER DRAFT OF THIS PROMPT
=================================================================
These are things the earlier version of this prompt asserted about the
codebase that are FALSE. Do not build to the old assumption.

1.1  MODULE NUMBER. This is not Module 18. Module 18 is the bulk resume
     intake feature (docs/modules/18-bulk-resume-intake.md), 19 is
     Onboarding & Documents, 20 is the live coding round, 21 is the
     public marketing website, 22 is Privacy & Consent. This is
     MODULE 23. Doc goes at docs/modules/23-forms-public-applications.md,
     migration at
     supabase/migrations/0033_module23_forms_public_applications.sql.

1.2  THE ONBOARDING PRECEDENT DOES NOT EXIST. The old prompt said the
     public page should be "consistent with how Module 17's Onboarding
     document links were scoped". Onboarding is Module 19, and its
     tokenised no-login link was explicitly NOT BUILT — the doc says so
     and lists why. The real precedents for a no-login candidate page
     are Module 15's /unsubscribe and Module 20's /coding. Copy those.

1.3  THE PUBLIC PATH DOES NOT USE RLS. The old prompt said the public
     submission endpoint should be "a token-scoped, unauthenticated
     path" enforced by policy. There is no such thing in this codebase
     and Supabase cannot express it: an anonymous request has no JWT for
     a policy to key on. The real pattern (lib/coding/candidate.ts) is:
       verify the signed token in application code
         -> createAdminClient()   (service role, BYPASSES RLS)
         -> every single query filters organization_id explicitly.
     Follow it exactly, including the failure mode: createAdminClient()
     returns null when the secret key is unset, and the route must then
     return a 503 "not configured", never fall through to an
     unauthorised read.

1.4  THE PUBLIC TOKEN SHOULD NOT BE A STORED RANDOM SLUG. The old prompt
     said "public_token (unique, unguessable — a UUID or long random
     slug)". This codebase already made the opposite choice twice, for
     a good reason spelled out at the top of lib/coding/token.ts: the
     token is a stateless HMAC, so a database dump contains no working
     links and there is no token column for a mistaken SELECT to leak.
     See section 4 for how to keep that property AND still support
     "regenerate link".

1.5  source = "Public Application Form" IS NOT A VALID VALUE.
     applications.source and candidates.source are both the Postgres
     enum public.candidate_source, whose values are: career_page,
     resume_upload, email, referral, job_board, agency_database, manual.
     Add a new value 'application_form' in the migration, following the
     guarded ALTER TYPE ... ADD VALUE pattern already used in
     supabase/migrations/0032_module21_privacy_consent.sql, and extend
     CANDIDATE_SOURCES + CANDIDATE_SOURCE_LABELS in lib/types.ts.
     TRAP: a newly added enum value cannot be USED in the same
     transaction that added it — so the ALTER must not sit in the same
     statement batch as an insert or a default that references it.

1.6  THE CANDIDATE TABLE DOES NOT HAVE THE COLUMNS THE OLD FIELD LIST
     ASSUMED. See the mapping table in section 6. Specifically:
     candidates.name is ONE column (not first/last), there is NO
     current-salary/current-CTC column (only expected_salary), and there
     are NO linkedin / portfolio / github columns.

1.7  DO NOT INVENT A CONFLICT TABLE. The old prompt said to "queue
     conflicting fields through the same conflict-review pattern".
     That pattern is concrete: bulk intake never writes a parsed field
     onto an existing candidate. It writes the proposal into
     resume_parse_results with reviewed_at = null, and Module 6's
     buildFieldComparisons / applyReviewDecisions (lib/resumes/review.ts)
     let a human accept or keep each field. Reuse that. The unresolved
     queue already surfaces on the job page via
     lib/intake/queries.ts listUnresolvedConflicts.

1.8  MODULE 15 IS BUILT — DO NOT "SKIP SILENTLY". The old prompt hedged
     that the notification hook might not exist. It does:
     'application_received' is already in COMMUNICATION_EVENTS
     (lib/communications/events.ts) and lib/intake/process.ts already
     calls trySendForEvent for it. Wire it for real.

1.9  QR GENERATION IS ALREADY SOLVED. `qrcode` is already a dependency
     and app/api/coding-sessions/[id]/qr/route.ts already renders one
     server-side. Add a sibling route; do not add a client-side QR
     library.

1.10 THERE IS NO RATE LIMITER TO REUSE. Nothing in lib/ does IP rate
     limiting today, so this module builds the first one — and it has to
     be durable, because the app runs serverless and an in-process Map
     is per-instance and resets constantly. See section 11.

1.11 submission_count AS A PLAIN COLUMN IS A LIE WAITING TO HAPPEN. Any
     signed-in user can PATCH it directly through PostgREST. Either
     derive it (count over form_responses) or maintain it with an
     AFTER INSERT trigger and REVOKE UPDATE on the column. Do not let
     the client set it.

1.12 job_screening_questions ALREADY EXISTS AND IS NOT THIS. That table
     (migration 0002, shown as "Screening questions" on the job page)
     feeds the Module 8 AI phone screen. It is NOT the application
     form's custom questions. Do not merge them, do not migrate one into
     the other, and make sure the job page's two cards read as clearly
     different things.

2. CORE PRINCIPLE — ONE FORM ENGINE, NOT TWO SYSTEMS
=================================================================
One reusable form builder. A job's public application form is just the
first form created against that engine, auto-generated with sensible
defaults when a job is created. Recruiters can also create standalone
forms later (pre-interview questionnaires, document collection) with the
same engine. Do not build a special-cased "job application form" system
alongside a generic one.

3. DATA MODEL
=================================================================
forms (
  id                uuid pk
  organization_id   uuid not null references organizations
  name              text not null
  description       text
  purpose           enum form_purpose: 'job_application' | 'pre_interview' | 'general'
  job_id            uuid null references jobs (set when purpose =
                    'job_application', null otherwise) — enforce that
                    pairing with a CHECK, not just in code
  status            enum form_status: 'draft' | 'published' | 'disabled'
  token_version     integer not null default 1   -- see section 4
  created_by        uuid references auth.users
  created_at, updated_at
)
  unique (job_id) where purpose = 'job_application'  -- one application
                                                      form per job

form_fields (
  id, form_id (on delete cascade), organization_id (denormalised so RLS
  can key on it without a join — same choice job_screening_questions
  made), field_key text, label text, field_type enum form_field_type
  ('short_text','long_text','email','phone','number','dropdown','radio',
   'checkbox','date','file_upload','url','yes_no'),
  options jsonb not null default '[]',
  required boolean not null default false,
  is_standard boolean not null default false,
  display_order integer not null,   -- name it display_order, matching
                                    -- job_screening_questions, not "order"
                                    -- ("order" is a reserved word)
  created_at
)
  unique (form_id, field_key)

form_responses (
  id, organization_id, form_id, application_id null, candidate_id null,
  raw_answers jsonb not null,     -- field_key -> value, verbatim
  resume_id uuid null references resumes,
  submitted_at timestamptz not null default now(),
  submitter_ip inet null,         -- see the privacy note below
  created_at
)

form_submission_attempts (          -- the rate limiter's ledger; see §11
  id, form_id, ip_hash text not null, attempted_at timestamptz not null
    default now()
)
  index (form_id, ip_hash, attempted_at desc)

RLS
  forms / form_fields / form_responses: organization-scoped SELECT for
  members via the existing is_org_member() helper. Writes restricted by
  role IN THE POLICY, not only in the route — AGENTS.md's rule, and it
  matters concretely here: without it a Viewer with a browser PostgREST
  client could publish a form, and publishing a form makes a URL
  world-reachable. Encode in WITH CHECK:
    - insert/update of forms and form_fields: Owner/Admin/Recruiter only
    - a status transition to 'published' or 'disabled': Owner/Admin/Recruiter
    - token_version bump: Owner/Admin only
    - form_responses: NO client insert path at all (the public route
      writes with the service role), members SELECT only, nobody UPDATEs
  form_submission_attempts: no client access whatsoever.

PRIVACY NOTE ON submitter_ip. An IP address is personal data under GDPR,
and Module 22 exists precisely so this product does not collect things
casually. Store a salted hash for rate limiting (that is all rate
limiting needs), and keep the raw IP only if the retention settings in
lib/privacy/settings.ts can express dropping it. If you store the raw
value, say so in the completion report and add it to the retention
sweep — do not leave it undocumented.

4. THE PUBLIC TOKEN
=================================================================
Copy lib/coding/token.ts's construction: an HMAC over the form id,
keyed on INTEGRATION_ENCRYPTION_KEY, base64url, version-prefixed.
Nothing secret stored in the database.

The one thing coding sessions did not need and this does is REGENERATION.
Sign over (form_id, token_version) and have the verifier check the
signature against the CURRENT token_version read from the row. Bumping
forms.token_version therefore invalidates every previously issued link
and QR code in one UPDATE, with no token column anywhere.

Rules:
  - No key set -> createAccessToken() returns null and publish is
    REFUSED with the actionable message (copy SIGNING_UNAVAILABLE_MESSAGE's
    wording). Never issue an unsigned link.
  - The URL exposes forms.id and nothing else. No organization id, no
    job id, no candidate id.
  - Revocation is expressed on the ROW, like coding sessions: status
    'disabled' stops the page from accepting submissions within the same
    request, without touching the token.
  - Regenerating is Owner/Admin only and must warn, before confirming,
    that every shared link and printed QR code stops working.

10. SUBMISSION FLOW — ORDER MATTERS
=================================================================
POST /api/apply/[token]/submit, multipart. Server-side, in this order:

  1. Verify the token signature against the row's current
     token_version. Load the form + fields with createAdminClient(),
     filtering organization_id explicitly.
  2. Reject if status != 'published' — with the neutral message.
  3. Rate-limit check (§11) BEFORE any file work.
  4. Validate the resume file BEFORE parsing: isAllowedResumeUpload()
     from lib/resumes/uploadPolicy.ts and a 10 MB cap
     (MAX_FILE_BYTES in app/api/jobs/[id]/intake/route.ts mirrors the
     bucket's file_size_limit — use the same number, and reuse
     RESUME_UPLOAD_REJECTION's wording). Rejections come back as inline
     field errors, not a generic 500.
  5. Re-validate EVERY field against its form_fields config. Never
     trust the client. Required, type shape, dropdown/radio values
     within options, numeric ranges that match the candidate column
     CHECKs from §6.
  6. Insert form_responses with raw_answers, application_id and
     candidate_id still null. The submission is now durable — this is
     the same "save the artifact first" ordering as the coding submit
     route.
  7. Store the file in the 'resumes' bucket under
     <organization_id>/... and insert the resumes row, mirroring
     lib/intake/process.ts. Compute file_hash the same way it does.
  8. extractResumeText() -> parseResume(). Both are expected to fail
     sometimes; a failure must NOT fail the submission. The candidate
     typed their details in; a broken PDF is not their problem and they
     must not be told to resubmit. Record the failure and continue.
  9. Duplicate match: normalizeEmail / normalizePhone
     (lib/candidates/dedupe.ts), then resolveCandidateMatch
     (lib/intake/match.ts). Do not write a second matcher.
       matched  -> do NOT create a candidate and do NOT overwrite their
                   profile. Write the parsed proposal to
                   resume_parse_results with reviewed_at null so it
                   surfaces in the existing conflict queue (§1.7).
                   Typed answers that conflict with the stored profile
                   go through the SAME review, not straight onto the row.
       no match -> create the candidate from the TYPED answers, then
                   fill only the still-empty fields from the parsed
                   resume. Typed wins over parsed wherever both exist —
                   the candidate told you that value directly.
 10. ensureApplicationForCandidate() from lib/intake/process.ts for the
     application. It already handles both the "already applied" SELECT
     and the 23505 unique-violation race on (candidate_id, job_id) —
     which a public endpoint will hit for real, because people
     double-tap Submit on a phone. Stage = DEFAULT_APPLICATION_STAGE
     from lib/applications/stages.ts, never a literal ('new' was
     renamed to 'applied' by migration 0021 and the literal silently
     broke intake once already). source = 'application_form' (§1.5).
 11. Patch form_responses.application_id / .candidate_id / .resume_id
     now that they are resolved.
 12. logActivity() from lib/activity/log.ts, and logAiCall() for the
     parse, exactly as intake does.
 13. trySendForEvent('application_received', ...) from
     lib/communications/triggers.ts, and dispatch() from
     lib/automations/engine.ts. Awaited — a serverless function can be
     frozen the moment it responds — but wrapped so neither can fail a
     submission that is already durable.
 14. Custom answers (is_standard = false) render as an "Application form
     responses" card on the Application detail page: label + answer, in
     display_order, including the standard fields that have no candidate
     column (§6).

If a step after 6 fails, the response is still recorded and visible to
recruiters with a clear "needs attention" state. A submission that
reached the database must never be silently dropped because a downstream
step broke — the candidate has already been told it worked.

=================================================================
11. RATE LIMITING AND ABUSE
=================================================================
There is nothing to reuse (§1.10), so build it durably: insert a row
into form_submission_attempts on every attempt, keyed by
(form_id, ip_hash), and reject when the count within the last hour
exceeds the cap (default 3). An in-memory counter would reset on every
cold start and is not a limit.

  - Hash the IP with a server-side salt; never key on the raw value.
  - Read the client IP from the platform header the way Next 16 exposes
    it on this deployment (check the runtime docs in
    node_modules/next/dist/docs/ — do not assume request.ip exists).
    If no IP can be determined, apply a per-form global cap rather than
    silently letting it through unlimited.
  - The limit message must be honest and human: "You've already
    submitted this application a few times. If something went wrong,
    contact the recruiter." Not "429".
  - Sweep old attempt rows (they are only useful for an hour).
  - Reject oversized or wrong-type files before parsing (§10 step 4) —
    parsing is the expensive path and must not be reachable by an
    anonymous caller with a 10 MB junk file.
