====================================================
PHASE 2 — THE ROUTING AND AUTH PROBLEM (SOLVE THIS FIRST)
====================================================

This is the single hardest part of the whole task. Address it explicitly before
building any UI.

Two facts about the current code make a public website impossible until they are
handled:

FACT 1 — The root route is not free.

app/page.tsx currently redirects "/" straight to /dashboard. A public landing
page wants that exact path.

FACT 2 — Auth is deny-by-default at the edge.

lib/supabase/session.ts holds a PUBLIC_PATHS allowlist. Anything not on that
list redirects an anonymous visitor to /login. That default is deliberate and
GOOD — a new module's routes are protected the moment they exist, without anyone
remembering to protect them. Do not weaken it.

So a new marketing page will 302 to /login until it is explicitly allowlisted.

Decide and justify an approach. Consider at least these options:

OPTION A — Route group in the same app

app/
├── (marketing)/
│      ├── layout.tsx      ← public shell: marketing header + footer
│      ├── page.tsx        ← "/" the landing page
│      ├── product/...
│      ├── how-it-works/
│      ├── docs/
│      └── contact/
└── (app)/                 ← existing private routes, unchanged

OPTION B — A single public prefix

/site/*  or  /www/*  — one allowlist entry, zero collision with "/"

OPTION C — A separate deployment entirely

A standalone marketing site on the apex domain, with the product app on a
subdomain (app.example.com).

For each option, tell me:

- How the allowlist entry is written, and whether it can over-match a private
  route (e.g. does a "/product" entry accidentally free "/products"?)
- What happens to "/" for an ANONYMOUS visitor
- What happens to "/" for a SIGNED-IN visitor (should they see marketing, or be
  sent to /dashboard? — this is a product decision, so ask me)
- Whether the private app shell leaks into the public layout
- Whether existing redirects (login's `next` param, the signed-in /login and
  /signup bounce to /dashboard) still behave correctly
- SEO and caching implications
- Risk of accidentally exposing something private

Recommend ONE and explain why. Then confirm with me before implementing.

CRITICAL RULE for the allowlist change:

The public marketing routes must be matched PRECISELY. When you add entries to
PUBLIC_PATHS, prove — in writing, and in a unit test — that:

- every intended public path is reachable while anonymous
- NO existing private route became public as a side effect
- a prefix entry cannot be extended into a private route by an attacker
  appending a path segment

Add a test for this. The allowlist is a security boundary now, not a
convenience list.

====================================================
PHASE 7 — SCREENSHOTS AND DEMO VISUALS
====================================================

Real visuals, captured from the running application.

PROCESS:

1. Seed a dedicated demo organization with clearly FICTIONAL data.
2. Run the app against that seed.
3. Capture screenshots of the real UI.
4. Optimise them and commit them under a public asset directory.
5. Reference them with explicit width and height to prevent layout shift.

ABSOLUTE RULE — NO REAL PERSONAL DATA IN A PUBLIC SCREENSHOT.

A screenshot of this product contains candidate names, emails, phone numbers,
resumes, salary expectations, interview feedback, and AI assessments of real
people. Publishing any of that on a marketing page is a data breach, and it is
irreversible the moment it is deployed — the image gets cached, indexed, and
scraped.

So:

- Every screenshot must come from purpose-built seed data with invented names,
  invented email addresses on a domain reserved for documentation, and invented
  companies.
- Never screenshot a live production or staging tenant.
- Before committing ANY image, verify it frame by frame: check the sidebar,
  breadcrumbs, notification badges, browser tabs, autofill dropdowns, avatars,
  toast messages, and any partially visible row at the edge of the viewport.
  Real data leaks at the margins of a screenshot far more often than in the
  middle of it.
- Do not blur or crop as the primary defence. Reseed and recapture instead.
- If a genuine screenshot cannot be produced safely, use an honest stylised UI
  illustration and do not present it as a photograph of the product.

Read docs/00-privacy-compliance.md before this phase and follow it.


====================================================
PHASE 8 — CONTACT / GET STARTED
====================================================

Make the CTAs actually work.

Flows to support:

- "Get started" → sign up (the existing /signup route)
- "Sign in" → the existing /login route
- "Contact us" / "Request a demo" → a public form
- "Talk to sales" → whatever real channel I confirm

THE PUBLIC FORM IS A SECURITY SURFACE. Treat it as one.

An unauthenticated write endpoint on a multi-tenant database is exactly the
thing this project's architecture rules are written to protect. Note carefully:
the browser holds an authenticated PostgREST client, and RLS — not the route
handler — is the real boundary. A public form makes that boundary reachable by
anonymous callers too.

Requirements:

- A dedicated table for inbound leads. It is NOT tenant-scoped in the normal
  sense, because a lead has no organization yet. Design its RLS explicitly:
  anonymous INSERT may be permitted, but anonymous SELECT, UPDATE, and DELETE
  must be impossible. Prove that an anonymous client cannot read back what
  anyone else submitted.
- Server-side validation of every field. Never trust the client.
- Rate limiting per IP and a spam defence. Say which you chose and why.
- A honeypot or equivalent that does not harm accessibility. No CAPTCHA that
  blocks keyboard or screen reader users.
- Length caps on every field, so the table cannot be used as free storage.
- Store the submission first, then notify. A failed notification must never
  lose the lead.
- Route notifications through the existing integration adapters in
  lib/integrations/ — do not re-implement an email call.
- Explicit consent language and a link to the privacy policy. Record what the
  person consented to and when.
- Honest success and error states. If the send fails, say so — never show a
  success message for a submission that did not persist.
- The form must not leak internal error details. Use the existing
  lib/api.ts error helpers.
- Where do these leads go? Ask me. Do not assume an inbox.

Migrations go in supabase/migrations/ as plain re-runnable SQL, following the
existing numbering and the `if not exists` / `drop policy if exists` style.

====================================================
PHASE 10 — PERFORMANCE, SEO, AND CORRECTNESS
====================================================

A marketing site has different constraints from a dashboard.

- Static rendering wherever possible. The public pages have no per-user state
  and must not be dynamically rendered per request. Verify the build output
  actually shows them as static.
- No public page may import a tenant helper, a session client, or the service
  role admin client. Add a check that enforces this — a public page that reads
  the session becomes dynamic and, worse, invites a data leak.
- Correct metadata on every page. Open Graph and Twitter cards with a real
  preview image.
- sitemap.xml and robots.txt, generated — and the sitemap must contain ONLY
  public URLs. Never list a private app route.
- JSON-LD structured data for the organization and the software product.
- Optimised images through the framework's image handling, with modern formats.
- No render-blocking third-party scripts. If analytics is wanted, ask me first
  and disclose it in the privacy policy — do not silently add a tracker.
- Do not regress the existing app's bundle. Report before-and-after sizes.
- Lighthouse: aim for 95+ on performance, accessibility, and best practices.
  Report the actual numbers you measured, not the numbers you hoped for.
