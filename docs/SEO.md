## 1. Analytics inventory — `MISSING`, deliberately

**There is no analytics on this site. None.**

Searched for, and absent from both the source and `package.json`: Google
Analytics, Google Tag Manager, GA4, `gtag`, `dataLayer`, Vercel Analytics,
Vercel Speed Insights, Plausible, PostHog, Mixpanel, Amplitude, Hotjar,
Microsoft Clarity and Segment. There is no third-party `<script>` on any public
page, and no custom event pipeline.

| | |
| --- | --- |
| Provider | none |
| Where loaded | nowhere |
| Data collected | none |
| Consent required | n/a |
| Performance impact | none |

**Module 29 did not add one, and that is a decision rather than an omission.**
Two reasons, the second of which is binding:

1. The module's own instruction is not to add a provider without a clear
   project-level reason. There is no measurement question anyone has asked that
   Search Console will not answer, and Search Console needs no code.
2. **The published Cookie Policy would become false.** `/cookies` states, in
   these words, that the public website sets no cookies, that there is no
   analytics of any kind, and — explicitly — *"If any of that is added later,
   this page and the privacy page change first, and a consent mechanism gets
   built at the same time — not afterwards."* Adding analytics in a module that
   was told not to touch legal content would break that promise on the day it
   shipped.

### If analytics is added later

The order is fixed by the sentence above, and it is not negotiable:

1. Decide the provider and what it actually collects.
2. Update `/cookies` and `/privacy` to describe it truthfully — including
   cookie names and durations, which must come from the provider's
   documentation and not be estimated.
3. Build the consent mechanism, and make the scripts load only after consent
   where the provider requires it.
4. Only then add the script.

A privacy-first provider that sets no cookies changes step 3, not steps 1–2.

## 2. Google Search Console — `MISSING`, and no token was invented

There is no verification meta tag, no `google*.html` file in `public/`, and no
DNS record this repository knows about.

**No placeholder token was added.** A fake `google-site-verification` value is
worse than none: it looks configured, so nobody checks, and verification
silently never happens.

### Setup — the manual steps

The site is ready for all of this today; none of it needs a code change.

1. Open Google Search Console.
2. Add a **Domain property** for `scoreboad.com` (not a URL-prefix property —
   a domain property covers `http`, `https`, `www` and every subdomain in one).
3. Google supplies a **DNS TXT record**.
4. Add that exact record in the domain's DNS (BigRock), at the apex.
5. Verify ownership. DNS propagation can take up to a few hours.
6. Open **Sitemaps** and submit `sitemap.xml`.
7. Open **URL Inspection**, test `https://scoreboad.com/`, and request indexing.

> **Nothing here claims the site is indexed.** It is not, as far as this
> repository can know. Indexing is evidenced in Search Console and nowhere else.

## 3. robots.txt — `VERIFIED`

Generated by `app/robots.ts`. Served at `/robots.txt`, 200.

- `Allow: /`, so every public marketing page is crawlable.
- `Host` and `Sitemap` both point at `https://scoreboad.com`.
- Disallows the application's routes (they redirect anonymous callers anyway)
  and — the ones that matter — `/apply/`, `/coding/` and `/unsubscribe`, which
  are public by design, authorised by a signed token, and must never appear in
  an index.

It is a crawl directive, not a security control. The tokens are what make those
routes safe.

## 4. sitemap.xml — `VERIFIED`

Generated by `app/sitemap.ts`. Served at `/sitemap.xml`, 200,
`application/xml`, parses as valid XML.

- **15 URLs, 15 unique.** No duplicates.
- Every URL is `https://scoreboad.com/…`. No query string, no `localhost`, no
  `*.vercel.app`.
- No private route, no token-authorised route, no 404.
- **No `lastModified`.** There is no reliable per-page modification date in this
  project, and stamping the deploy time told crawlers that every page changed on
  every deploy. Omission is honest; invention is not.
- `/login` and `/signup` are deliberately absent: a sign-in form is a control,
  not content. Both stay crawlable and linked.

## 6. Weekly monitoring workflow

Once verification is done, this is the whole routine. It takes ten minutes.

**Performance → Search results**
Clicks, impressions, CTR, average position. Read the *top queries* and *top
pages* tables together: a page with impressions and no clicks usually has a
title or description problem, which is a one-line fix in `lib/marketing/seo.ts`
or the page's `buildMetadata()` call.

**Indexing → Pages**
Indexed vs not indexed, and the reason given for each exclusion. Expect
`/login` and `/signup` to sit outside the sitemap; anything else excluded is
worth reading.

**Sitemaps**
Status and last read date. A sitemap that stops being read is usually a
deployment problem, not an SEO one.

**Security & Manual Actions**
Should stay empty. If a manual action ever appears, the most likely cause on
this site would be structured data describing something a visitor cannot see —
which `faq.test.ts` and `seo.test.ts` exist to prevent.

**Core Web Vitals**
Needs field data, so it stays empty until there is real traffic. See §8.

## 7. Issue priority

| Priority | Symptom |
| --- | --- |
| **Critical** | A public page is not indexable · wrong canonical · sitemap 404s or fails to parse · robots blocks a public page · metadata resolves to a non-production domain |
| **High** | An important page excluded from the index · a broken internal link · two pages sharing a canonical · wrong title or description on a core page |
| **Medium** | Missing metadata · weak internal linking to a page · image alt problems |
| **Low** | Wording refinements · minor content improvements |

Several of the Critical and High rows are already enforced by
`lib/marketing/seo.test.ts`, `footer.test.ts` and `faq.test.ts` — a broken
canonical, a private route in the sitemap, a sitemap/robots contradiction or an
orphaned page fails the build rather than waiting to be noticed in a report.

## 8. Core Web Vitals — `NOT VERIFIED`

No monitoring provider is installed, and **LCP, INP, CLS and TTFB have not been
measured** for this site. There is no browser in the build environment and no
field data without traffic.

What IS measured, from a production server, is payload — see
`docs/Memory.md` (Module 27): 52.3K HTML, 216.3K JS and 109.0K CSS gzipped on
the home page, of which 79.6K is Bulma the marketing pages do not use.

Two ways to get real numbers, in order of cost:

1. **Search Console → Core Web Vitals**, once there is traffic. Field data from
   real Chrome users, free, and no code.
2. A monitoring provider (Vercel Speed Insights is the lowest-friction option on
   this host). Adding one is subject to §1's ordering — it is a third-party
   script and the Cookie Policy has to be true first.
