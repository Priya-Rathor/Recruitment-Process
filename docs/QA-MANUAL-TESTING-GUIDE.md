# 1. Project Overview

## 1.1 What this project does

**Recruitment OS** is a multi-tenant, AI-assisted recruitment operating system —
an applicant tracking system (ATS) that carries a candidate from first resume to
signed onboarding documents, with AI assistance layered on top of (never instead
of) the manual workflow.

It covers the entire hiring lifecycle:

```
Job requisition
   → Candidate intake (manual, single resume upload, or bulk drop)
   → Resume text extraction + AI parsing + human review
   → Application created (candidate × job)
   → AI match scoring (deterministic + optional semantic)
   → AI voice screening call (Bolna) + AI screening report + human correction
   → Structured evaluations (phone / video / written assessment / director round)
   → Interviews, scheduling, calendar invite, structured feedback
   → Client submission + client feedback clock (agency mode only)
   → Hired
   → Onboarding document checklist → verified → Completed
```

Running alongside all of that:

- an **automation engine** (trigger → conditions → actions, with an approval queue,
  a daily cap, and an organization-wide kill switch),
- an **append-only activity/audit log**,
- **internal notifications** (in-app + optional email) and **candidate
  communications** (email + WhatsApp templates with a mandatory unsubscribe),
- **analytics** with CSV export and an "Ask Analytics AI" explainer,
- **settings & integrations** (Bolna, Google Calendar, Email, WhatsApp, LLM, n8n).

## 1.2 What problem it solves

Recruitment teams lose time on three things this product attacks directly:

| Problem | How the product answers it |
| --- | --- |
| Resumes arrive as unstructured files; someone re-types them | Text extraction + AI parsing into a reviewable structured diff |
| Early screening calls are repetitive and eat recruiter hours | Automated outbound voice screening with a consent disclosure, transcript, and AI report |
| "Where is everybody?" is answered by memory and spreadsheets | A stage pipeline with SLA aging, an attention queue, and an audit trail |
| Candidates go dark because nobody remembered to email them | Event-triggered templated messages with an opt-out that cannot be removed |
| Managers cannot see what is actually happening | Analytics with a funnel, time-to-hire, bottleneck detection, and honest "not enough data" states |

## 1.3 Who the users are

Four roles, defined as a PostgreSQL enum `public.org_role` and enforced in
**both** the API layer (`requireRole()`) and in Row-Level Security policies:

| Role | Who they are | Broad capability |
| --- | --- | --- |
| **owner** | Created the workspace | Everything. Only an Owner may grant/revoke Owner. At least one active Owner must always exist. |
| **admin** | Ops / hiring lead | Everything except changing Owner access and deleting the org. Manages settings, integrations, automations, templates. |
| **recruiter** | Day-to-day recruiter | Creates and works jobs, candidates, applications, interviews, clients. **Scoped to their own work** on Dashboard, Pipeline, Applications and Analytics. Cannot manage settings, automations, integrations, invites, or the audit log. |
| **viewer** | Read-only stakeholder | Reads almost everything. Cannot create, edit, send, upload, trigger AI writes, or export analytics. |

There is a **fifth party who is not a user**: the **candidate**. Candidates have
no login. They touch the product in exactly two places — they receive templated
emails/WhatsApp messages, and they can open the signed `/unsubscribe` link. That
page is the only public authenticated-by-token surface in the product.

**Crucial architectural fact for testers:** the browser holds an *authenticated
PostgREST client*. Any signed-in user can, in principle, write directly to the
database and skip an API route entirely. This is why every meaningful rule is
enforced **twice** — once in the route handler (for a friendly error message) and
once in an RLS policy or database trigger (for the actual security boundary).
When you test permissions, a passing UI test is only half the test.

## 1.6 The complete application flow

```
1.  Visitor lands on /            → redirect /dashboard
2.  proxy.ts sees no session      → redirect /login?next=/dashboard
3.  /signup → Supabase signUp     → email confirmation (if enabled)
4.  /auth/callback?code=…         → exchangeCodeForSession → /onboarding
5.  /onboarding                   → create_organization_and_owner() RPC
                                     → org + owner membership in one transaction
                                  → optional AI setup recommendations (Owner/Admin)
                                  → agency_mode chosen here (clients on/off)
6.  /dashboard                    → KPI tiles, attention queue, daily AI brief
7.  /jobs/new                     → paste JD → AI extract → review → save
8.  /jobs/[id]                    → Hiring Stages config, Add candidates (bulk intake)
9.  /candidates/new  OR bulk drop → dedupe check → candidate record
10. /candidates/[id]/resume       → upload → extract → AI parse → review diff → apply
11. /applications/new             → candidate × job → application at stage "applied"
12. /applications/[id]            → match score, stage moves, notes, timeline
13. …/screening-call              → start Bolna call (consent disclosure is structural)
    ← POST /api/webhooks/bolna    → transcript + status + consent recorded
14. …/screening-report            → AI summary → human corrects → ai_* columns frozen
15. …/match, …/interview-brief    → AI reading aids, nothing saved
16. Evaluations logged per stage  → verdict + next action
17. /interviews                   → schedule (+ optional Google Calendar invite)
                                  → structured feedback → trigger completes interview
18. …/submission (agency mode)    → draft → SEND → client feedback clock opens
19. Stage → hired                 → DB trigger creates onboarding_record + checklist
20. /hires/[id]                   → upload / verify / reject documents
                                  → all required verified → Mark complete
21. Throughout: automations fire, notifications land, activity_events append,
    candidate messages send with an unmovable unsubscribe footer,
    analytics recompute from the same query layer the screen uses.
```

# 2. Architecture Overview

## 2.1 Tenant isolation — the single most important rule

`lib/tenant.ts` is the contract every module inherits:

| Function | Used by | On failure |
| --- | --- | --- |
| `getCurrentUser()` | anything | returns `null`; **self-heals** a valid session with no `public.users` row by calling the `ensure_current_user_profile()` RPC (prevents an infinite redirect loop) |
| `requireCurrentUser()` | API routes | throws `TenantError(401)` |
| `requireMembership()` | API routes | throws `TenantError(403)` if the user belongs to no org |
| `requireRole([...])` | API routes | throws `TenantError(403)` naming the required role and the caller's role |
| `requireMembershipOrRedirect()` | **pages** | `redirect("/login")` or `redirect("/onboarding")` — never throws |
| `getCurrentOrganizationId()` | API routes | the server-resolved tenant id |

The active organization comes from a cookie `active_organization_id`, but that
cookie is **a hint only** — it is validated against a real `organization_members`
row every time. A forged cookie yields the user's default org, never someone
else's tenant.

**Known trap (documented in `AGENTS.md`, worth re-testing):**
`organization_members`' SELECT policy deliberately exposes *every* member row of
an org you belong to (the team list needs it). Any query asking "what is *my*
membership?" **must** filter `user_id` explicitly or it picks up a teammate's
role. `getUserMemberships()` does filter correctly.

## 2.2 Layer-by-layer

**Edge (`proxy.ts` → `lib/supabase/session.ts`)**
Deny-by-default. Public paths are exactly:
`/login`, `/signup`, `/forgot-password`, `/reset-password`, `/invite`, `/unsubscribe`.
`/api/*` and `/auth/*` are passed through so they can return JSON 401s rather than
HTML redirects. A signed-in user hitting `/login` or `/signup` is bounced to
`/dashboard`. The `?next=` parameter is preserved and is validated as a
same-origin relative path (`/^\/(?!\/)/`) before use in both `LoginForm` and
`/auth/callback` — so it cannot become an open redirect.

**Pages** — Server Components by default, `export const dynamic = "force-dynamic"`
on every data-bearing page so "today" never goes stale. Data loads through
`lib/<module>/queries.ts`, never through client-side fetch effects. After a
mutation, client components call `router.refresh()`.

**API routes** — 83 `route.ts` files. Every one wraps its body in
`try { … } catch (error) { return handleRouteError(error) }`. `handleRouteError`
turns a `TenantError` into its own status and everything else into a **generic
500** so internals and raw provider/database errors never reach the browser.

**Database** — 42 tables, all with `organization_id` and RLS. 59 triggers enforce
invariants that a route handler cannot (see §Database Documentation). Helper
functions `is_org_member()` / `has_org_role()` are `SECURITY DEFINER` with a
pinned `search_path`, which is what lets them run inside another table's policy
without recursing.

**Service-role client (`lib/supabase/admin.ts`)** — bypasses RLS. It exists for
exactly two reasons: integration credentials are protected by a **column-level
REVOKE** so even an Owner's session cannot read the ciphertext, and the Bolna
webhook / cron sweep have no session at all. Every query made with it must filter
`organization_id` explicitly. It returns `null` when unconfigured, so features
degrade to "not configured" rather than crashing.

## 2.3 The AI safety model

```
Raw Data → AI → Structured Output → Validation → Human Review → Business Action
```

- `lib/ai/provider.ts` is the **only** file that talks to an LLM. There is
  deliberately **no generic `askAI()`** — each feature is a named function.
- Every AI function returns `AiResult<T>` = `{ok:true,data}` | `{ok:false,code,message}`
  with `code` ∈ `not_configured` | `provider_error` | `invalid_output`.
  AI failure is an **expected state**; the manual workflow must always remain usable.
- Output is JSON-mode, schema-validated by a `validate()` callback before it is
  ever rendered. Invalid output is rejected, not shown.
- 30-second abort budget. AI must never hang a request.
- **AI never writes to a trusted table directly.** `ai-action` endpoints return
  `{ data, saved: false }`.
- The screening report keeps `ai_*` columns frozen forever (a trigger refuses to
  update them) so "what did the AI actually say?" always has an answer.
- `lib/ai/numericGuard.ts` enforces that the Daily Brief never states a number
  that contradicts the KPI tiles — and that enforcement is unit-tested.

## 2.4 Fail-closed rules (safety-critical, test these hard)

| Rule | Where enforced |
| --- | --- |
| Integration credentials are AES-GCM encrypted; **no `INTEGRATION_ENCRYPTION_KEY` → adapters refuse to connect** | `lib/integrations/crypto.ts` |
| Bolna webhook: **no `BOLNA_WEBHOOK_SECRET` → 503, every request rejected**; otherwise constant-time HMAC over raw bytes | `app/api/webhooks/bolna/route.ts` |
| Cron sweep: **no `CRON_SECRET` → 503**, never open | `app/api/automations/sweep/route.ts` |
| Screening call consent disclosure cannot be disabled; `consent_confirmed` is stamped by a trigger; Module 9 refuses a transcript without it | `trg_screening_calls_consent`, `lib/screening/script.ts` |
| Screening retry cap: default 3, hard max 5, min delay 15 min | `lib/screening/retry.ts` |
| `callback_requested` is **never** auto-retried | `TERMINAL_STATUSES` |
| Unsubscribe footer is appended by the send pipeline *after* rendering — a template cannot delete it | `lib/communications/optout.ts` |
| No signing key → footer degrades to "reply and ask to be removed" rather than emitting a dead link | same |
| Message templates ship **inactive** — a product update never starts emailing candidates | `message_templates.active default false` |
| Automations always create as `draft`; `status` is not read from the create body at all | `POST /api/automations` |
| Organization-wide automation kill switch checked **before a single rule is loaded** | `lib/automations/engine.ts` |

# 4. MODULE M01 — Authentication & Session

## 4.1 Purpose

Gets a real human into a real workspace, and keeps everyone else out. It is the
foundation every other module inherits: no page in the product renders without a
session, and no API route acts without one.

**Who uses it:** everybody, once, then invisibly on every request.
**Problem solved:** a multi-tenant product where the wrong person seeing the wrong
candidate's phone number is a legal problem, not just a bug.

## 4.3 Complete User Flow — Sign up

```
Step 1  User opens /signup
Step 2  User types name, email, password (≥8 chars)
Step 3  User clicks "Create account"
Step 4  FRONTEND validates password length locally (before any network call)
Step 5  supabase.auth.signUp() is called DIRECTLY from the browser
        (this is not an API route of ours)
Step 6  Supabase creates auth.users row
Step 7  DB TRIGGER on_auth_user_created → handle_new_auth_user()
        inserts public.users (auth_id, name, email, avatar_url)
        (skips silently if the identity has no email — phone-only auth)
Step 8  If email confirmation is ON: no session returned →
        UI swaps to "Check {email} for a confirmation link"
        If confirmation is OFF: session returned → router.push("/onboarding")
Step 9  User clicks the emailed link → /auth/callback?code=…&next=/onboarding
Step 10 exchangeCodeForSession(code) → session cookie set
Step 11 `next` is validated as same-origin relative → redirect /onboarding
```

**USER ACTION** → **FRONTEND** (local length check) → **SUPABASE AUTH** (no API
route of ours) → **DB TRIGGER** (`public.users` row) → **EMAIL** → **/auth/callback**
(code exchange) → **UI RESULT** (/onboarding).

## 4.4 Complete User Flow — Sign in

```
Step 1  User opens a protected page, e.g. /candidates
Step 2  proxy.ts runs, calls supabase.auth.getUser(), finds no user
Step 3  proxy.ts redirects to /login?next=/candidates
Step 4  LoginForm reads ?next, validates it matches /^\/(?!\/)/
Step 5  User enters credentials, clicks Sign in
Step 6  supabase.auth.signInWithPassword()
Step 7  On failure: generic message — "That email and password combination
        didn't work." (deliberately does NOT reveal whether the account exists)
Step 8  On success: router.push(next); router.refresh()
Step 9  proxy.ts now sees a session, allows the page
Step 10 Page calls requireMembershipOrRedirect()
        - no public.users row → self-heals via ensure_current_user_profile() RPC
        - no organization    → redirect /onboarding
        - otherwise          → render
```

## 4.5 Technical Flow

- **Session storage:** Supabase auth cookies, refreshed on *every* matched request
  by `updateSession()`. The matcher excludes `_next/static`, `_next/image`,
  `favicon.ico` and image extensions.
- **Self-healing profile:** if a session exists with no `public.users` row (signed
  up before migration 0001, or a window where the trigger was missing),
  `getCurrentUser()` calls the `ensure_current_user_profile()` RPC, which reads
  `auth.uid()` only and cannot create anyone else's profile. Without this the
  symptom was `ERR_TOO_MANY_REDIRECTS`.
- **Open-redirect defence:** `next` is regex-validated in *two* places —
  `LoginForm` and `app/auth/callback/route.ts`.

## 4.6 API Flow

| API | Method | Auth | Notes |
| --- | --- | --- | --- |
| `/auth/callback` | GET | none (code is the credential) | `?code` + `?next`. Missing code → `/login?error=missing_code`. Exchange failure → `/login?error=auth_failed`. |

Login, signup, password reset and sign-out do **not** go through our API — they
call Supabase Auth directly from the browser.

## 4.7 Database Flow

```
auth.users  (Supabase-managed)
   │ INSERT triggers on_auth_user_created
   ▼
public.users (id, auth_id UNIQUE FK→auth.users ON DELETE CASCADE,
              name, email, avatar_url, created_at)
   │
   ▼ referenced by organization_members.user_id
```

# 5. MODULE M02 — Organization & Workspace Onboarding

## 5.1 Purpose

Turns a bare authenticated user into a tenant. Creates the organization, makes
the creator its Owner, captures the facts every later module reads (timezone,
industry, size, **agency mode**), and optionally asks the AI for setup
recommendations that are shown but never auto-applied.

**Who uses it:** whoever creates the workspace (becomes Owner); Owners/Admins
later, from `/settings/organization`.
**Problem solved:** a product where "today" means different things to different
people, and where an in-house team is shown a Clients module that is empty by
definition.

## 5.5 Database Flow

```
USER ACTION  "Continue"
 → API       POST /api/organizations
 → BACKEND   requireCurrentUser() + name validation
 → DATABASE  rpc create_organization_and_owner()
               INSERT public.users (upsert, defensive)
               INSERT public.organizations
               INSERT public.organization_members (owner, active)
 → RESPONSE  201 {data: organization}
 → UI        wizard step 2
```

`organizations` columns: `id, name, industry, size, country, timezone (NOT NULL
DEFAULT 'Asia/Kolkata'), agency_mode (NOT NULL DEFAULT true), automations_enabled,
onboarding_answer, onboarding_completed_at, created_at`.

**Agency-mode read rule:** always through `isAgencyMode()`, which returns
`organization?.agency_mode !== false`. An unmigrated/absent value reads as
**agency**, because that is what every org was before the flag existed. Reading it
the other way would silently blank the Clients module out of a live agency.

## 6.3 Complete User Flow — invite → accept

```
USER ACTION   Owner types colleague@x.com, picks "recruiter", clicks Send invite
→ FRONTEND    POST /api/invites {email, role}
→ BACKEND     requireRole(["owner","admin"])
              validate email shape → 400 "Enter a valid email address."
              validate role       → 400 "Select a valid role."
              if role==="owner" and caller is admin → 403
                "Only an Owner can invite another Owner."
              if a pending invite already exists → 409
                "An invite for this email is already pending."
→ DATABASE    INSERT invites (token uuid default gen_random_uuid(),
              expires_at default now()+7 days, status 'pending')
→ RESPONSE    201 {data: invite}
→ UI          Row appears in Pending invites

USER ACTION   Colleague opens /invite/{token}
→ proxy.ts    /invite is a PUBLIC path — page renders signed out
→ FRONTEND    If signed out: Sign in (?next preserved) / Create account
              If signed in: "Accept as {email}" + Accept invite
→ API         POST /api/invites/accept {token}
→ BACKEND     requireCurrentUser() only — the TOKEN is the credential
→ DATABASE    rpc accept_invite(p_token) — SECURITY DEFINER, does ALL validation:
                token exists? still pending? not expired?
                upserts public.users, INSERTs organization_members,
                marks the invite 'accepted'
              organization_members has NO client-facing INSERT policy, so this
              RPC is the only path in.
→ RESPONSE    {data:{organization_id}} and the active-org cookie is set
→ UI          router.push("/dashboard") — the new member is in
```

## 6.4 API Flow

| API | Method | Auth | Errors |
| --- | --- | --- | --- |
| `/api/members` | GET | any member | 400 invalid `status`/`role` filter |
| `/api/members/[id]` | PATCH `{role}` | **owner/admin** | 400 invalid role; 403 non-Owner touching Owner access; 404 not found/inactive; **409 last-Owner**; `{changed:false}` when the role is unchanged |
| `/api/members/[id]` | DELETE | **owner/admin** | 403 non-Owner removing an Owner; **409 last-Owner**; 404 |
| `/api/invites` | GET | **owner/admin** | 400 invalid status filter |
| `/api/invites` | POST `{email, role}` | **owner/admin** | 400 email/role; 403 admin inviting an Owner; 409 duplicate pending |
| `/api/invites/[id]` | DELETE | **owner/admin** | 404 "Pending invite not found." |
| `/api/invites/accept` | POST `{token}` | signed-in | 400 "Invite token is required."; 400 "This invite link is no longer valid. Ask for a new invite." |

## 6.5 Database Flow

`invites (id, organization_id, email CHECK position('@' in email) > 1, role,
token uuid UNIQUE, invited_by FK→users ON DELETE SET NULL, expires_at DEFAULT
now()+7 days, status CHECK IN ('pending','accepted','revoked','expired'), created_at)`

`organization_members (id, organization_id, user_id, role org_role, status
CHECK IN ('active','removed'), invited_by, joined_at, UNIQUE(organization_id,user_id))`

**Last-Owner protection is a database constraint trigger** (`enforce_owner_remains()`),
not just an API check — because a check-then-write across two statements is a
TOCTOU race. The route also counts remaining Owners for a friendly message and
translates the trigger's violation back into the same 409.

## 6.8 Known Risks — M03

1. **No invite email is sent.** `POST /api/invites` creates the row and returns
   `{data, invite_url}` — the link is handed to the Owner/Admin **once**, in the
   response, to share by hand. The code comment says Module 15 will email it
   later; it does not today. Confirm the UI actually surfaces `invite_url`,
   because if it does not, an invite is created that nobody can use.
2. **VERIFIED GAP — the invite token is not bound to the invited email address.**
   `accept_invite(p_token)` looks the invite up by token, checks only
   `status='pending' and expires_at > now()`, and then inserts a membership for
   **whoever is signed in** — it never compares `invites.email` with the caller's
   address. Anyone who obtains or guesses a token (it is a UUIDv4, so guessing is
   impractical, but forwarding is not) joins the organization at the invited
   role. The page text "Use the email address the invite was sent to" is advice,
   not enforcement. Test TC-TEAM-021 deliberately and file it.
3. **`ON CONFLICT … DO UPDATE SET role = excluded.role, status = 'active'`** in
   `accept_invite` means an existing member who accepts a *new* invite has their
   role **overwritten**, and a previously `removed` member is silently
   reactivated. An Admin holding a stale "viewer" invite link can demote
   themselves by accident; more importantly, a removed member who kept an old
   pending invite link can restore their own access. Worth testing directly.
4. Expired invites are never swept to `status='expired'`; expiry is only
   evaluated at accept time, so the Pending list can show links that no longer work.

# 7. MODULE M04 — Dashboard

## 7.1 Purpose

The first screen after sign-in. Answers two questions in one glance: *what
happened today?* (six KPI tiles) and *what needs me right now?* (the attention
queue), with an optional AI-written Daily Operations Brief above them.

**Who uses it:** everyone. A **Recruiter sees only their own workload**
(`scopeForRole()` returns `"own"`); Owner/Admin/Viewer see the whole organization.

**Problem solved:** a dashboard that reports a fake `0` when its query failed is
worse than no dashboard — it is a false statement to a manager. This module's
whole design is about never doing that.

## 7.3 Complete User Flow

```
Step 1  User signs in → /dashboard
Step 2  PAGE: requireMembershipOrRedirect() resolves the tenant + role
Step 3  resolveTimeZone(organization.timezone) — the ORG's zone, never the browser's
Step 4  Header paints immediately (org name, date, invite button)
Step 5  <Suspense> streams DashboardContent
Step 6  getDashboardData({organizationId, role, recruiterUserId, timezone})
          - dayRangeInZone() computes a HALF-OPEN [start, end) for "today"
          - six independent metric queries, each degrading on its own
          - the attention query, with its own status
Step 7  DailyBrief renders (with hasAnyData so it can refuse to narrate nothing)
Step 8  KpiTiles render, tinting only non-zero negative metrics
Step 9  AttentionQueue renders one of FOUR states: error / pending / empty / list
Step 10 User clicks an attention row → /applications/{id}
```

**USER ACTION** (open dashboard) → **SERVER COMPONENT** (no client fetch) →
**6 + 1 parallel Supabase queries** → **degradation logic per metric** →
**UI RESULT** (tiles + queue, each honestly labelled).

## 7.4 Technical Flow — the degradation rules (the heart of this module)

`isMissingRelation(error)` returns true **only** for `42P01` (undefined_table),
`PGRST205` (not in schema cache), `PGRST200` (missing embedded relationship), or
a message containing "does not exist" / "could not find the table" / "schema cache".

Anything else — an **RLS denial (42501)**, a statement timeout, a network fault —
is a real failure and surfaces as `status:"error"`. This narrowness is deliberate:
reporting a genuine bug as "not built yet" would hide it.

`OVERDUE_DAYS = 3` is the fallback threshold; `buildOverdueClause()` prefers the
per-stage SLA target from `pipeline_sla_config` via `targetDaysFor()`.

## 7.5 API Flow

| API | Method | Auth | Purpose | Notes |
| --- | --- | --- | --- | --- |
| `/api/dashboard` | GET | any member | KPI snapshot + attention queue as JSON | The page itself does **not** call this — it loads server-side. This exists for external/programmatic use. |
| `/api/dashboard/ai-action` | POST | any member | Generate the Daily Operations Brief | **Response-cached in-process**, keyed on the figures themselves, so the brief regenerates when a number moves. Cache is per-instance and does not survive a redeploy. |

The brief is derived **strictly** from the counts the dashboard already computed,
and `lib/ai/numericGuard.ts` enforces that it never states a number contradicting
a tile. That guard is unit-tested (`generateDailyBrief.test.ts`).

## 7.6 Database Flow

Reads only. Owns **no tables**:

```
candidates          → newCandidates      (created within today's [start,end))
screening_calls     → screeningsCompleted, failedCalls
interviews          → interviewsToday
applications (+ application_stage_history, pipeline_sla_config)
                    → overdueApplications, attention queue
automation_runs     → failedAutomations
```

| --- | --- | --- |

# 9. MODULE M06 — Job Hiring Stages

## 9.1 Purpose

Per-job configuration of which pipeline steps exist and what the AI says during
them. Four steps can be switched on or off per job; a fifth (resume scoring)
always runs and the toggle instead chooses between the platform default and this
job's own prompt.

**Who uses it:** Owner/Admin/Recruiter configure; **Viewer can see which stages
are enabled** (explicitly required) but cannot change them.

## 9.2 The five stages (`lib/hiring-stages/catalog.ts`)

| `stage_key` | Label | Kind | Execution | Engine |
| --- | --- | --- | --- | --- |
| `resume_score` | Resume Score | **scoring** | live | Module 7 matching |
| `ai_screening_call` | AI Screening Call | pipeline | **live** | Bolna (Module 8) |
| `phone_interview` | Phone Interview | pipeline | **configuration_only** | none |
| `video_interview` | Video Interview | pipeline | **configuration_only** | none |
| `written_assessment` | Written Assessment | pipeline | **configuration_only** | none |

**This is the most important honesty test in the module.** Only the AI Screening
Call is wired to a real engine. The other three save configuration and nothing

which would be false and alarming.

# 10. MODULE M07 — Bulk Resume Intake

## 10.1 Purpose

Drop a folder of resumes onto a job and let the product do the work: extract text,
AI-parse it, decide **deterministically** who each file belongs to, create or match
the candidate, store the resume, queue any profile disagreements for review, and
create the application.

**Who uses it:** Owner/Admin/Recruiter, from the "Add candidates" modal on a job.
**Problem solved:** the single most repetitive task in agency recruitment.

## 10.2 The governing design rule

> **Every file resolves independently.** One corrupt PDF among ten must not cost
> the other nine.

This is structural, not a promise: **one file per HTTP request**. There is no
shared transaction, no shared array, and no way for one file's failure to reach a
sibling. A processing exception is caught and recorded as a `failed` **row with
HTTP 200**, so the batch keeps its shape and the file can be retried.

## 10.3 The eight intake statuses (`lib/intake/status.ts`)

| Status | Meaning |
| --- | --- |
| `queued` | Accepted, not yet processed |
| `processing` | In flight |
| `candidate_created` | New person created + application created |
| `candidate_matched` | Matched an existing candidate + application created |
| `already_applied` | Matched, but an application for this job already existed |
| `match_conflict` | **Ambiguous — nothing was created.** File parked at `<org>/_intake/…` so it can still be downloaded and read |
| `manually_connected` | A human resolved a conflict via the override |
| `failed` | Extraction, parsing, or storage failed; `error_message` says why |

## 10.4 The matching rule (`lib/intake/match.ts`) — deterministic, never AI

Collect every candidate id the **normalised email** matches and every id the
**normalised phone** matches, then take the **union**:

| Union size | Outcome |
| --- | --- |
| 0 | `create` |
| 1 | `match` (even if only one field matched) |
| 2+ | `conflict` — resolve nothing |

Conflict reasons: `email_phone_disagree` (email says one person, phone says
another), `email_ambiguous` (one address already on two records),
`phone_ambiguous`.

**Why the union and not a sequence:** checking email first and taking the hit
would silently pick the email's owner in exactly the shared-family-phone case
that must not be guessed at.

**Normalisation** (`lib/candidates/dedupe.ts`, kept in sync with the DB trigger
`normalize_candidate_contact()`):
- Email: lowercase + trim. Deliberately **no** gmail dot/plus stripping.
- Phone: digits only, compared on the **last 10** (`PHONE_MATCH_DIGITS`). So
  `+91 98765 43210`, `098765 43210` and `9876543210` are one person. Shorter
  strings are kept as-is.

## 10.5 What the AI is and is not allowed to do here

- The AI **parses**, and that is all.
- It **never** decides who the resume belongs to (that is `match.ts`, deterministic).
- It **never** overwrites a field on an existing candidate — the proposal is
  queued as an unreviewed `resume_parse_results` row and counted in
  `queued_conflict_count`, which is what lets the modal say "3 profile updates
  need your review".
- The one place parsed values reach `candidates` directly is when creating a
  **brand-new** record, where there is nothing to overwrite.

## 10.6 UI Components

| UI Component | Purpose | User Action | Expected Result |
| --- | --- | --- | --- |
| **Add candidates** button on `/jobs/[id]` | Opens `IntakeModal` | Click | Modal opens |
| Drop zone / file picker | Select files | Drop or browse | `accept` = `RESUME_UPLOAD_ACCEPT` (.pdf,.doc,.docx + MIME types) |
| Per-file row | Progress + outcome | — | Filename, size, status chip toned by `INTAKE_TONE` |
| Summary line | `summaryLine(summarize(statuses))` | — | One sentence a recruiter actually reads |

## 10.7 Complete User Flow

```
Step 1  Recruiter opens /jobs/{id}, clicks Add candidates
Step 2  Drops 10 PDFs
Step 3  FRONTEND generates ONE batch_id (uuid), then POSTs each file separately
Step 4  For EACH file: POST /api/jobs/{id}/intake  (multipart)
        BACKEND:
          requireRole(["owner","admin","recruiter"])
          getJobDetail → 404 if not this org's job
          409 if the job is ARCHIVED ("Restore it before adding candidates.")
          400 if no file / empty file
          400 if size > 10 MB
          batch_id validated as a UUID, else a fresh one is generated
          isAllowedResumeUpload(name, type) → EXTENSION FIRST, MIME as fallback
            (browsers disagree about .doc's MIME type)
            → on rejection: a `failed` ROW with HTTP 200, so the batch continues
          hashFile(buffer) → SHA-256 (used to skip re-parsing unchanged files)
        processIntakeFile():
          extractResumeText()  → unpdf / mammoth / word-extractor
          parseResume()        → AI, schema-validated
          resolveCandidateMatch() → create | match | conflict
          create  → INSERT candidates (parsed values allowed: nothing to overwrite)
          match   → queue field conflicts as resume_parse_results (UNREVIEWED)
          conflict→ store the file at <org>/_intake/…, keep parsed_json, STOP
          store the resume in the private `resumes` bucket
          ensureApplicationForCandidate() → application at DEFAULT_APPLICATION_STAGE
          logActivity + logAiCall
          dispatch() automations (application_created trigger)
          trySendForEvent() candidate communication
Step 5  Each response returns one `resume_intake_items` row
Step 6  UI updates that row's chip; other files keep going
Step 7  Recruiter resolves any conflicts via the candidate picker

        → status becomes `manually_connected`
```

## 11.3 Complete User Flow — create with a duplicate warning

```
Step 1  Recruiter clicks Add candidate
Step 2  (Optional) pastes a blurb, clicks Structure with AI
        → POST /api/candidates/ai-action  (Viewer denied)
        → structureCandidateText() returns proposals, saved:false
        → diff table: Field | Yours (kept) | AI suggestion
Step 3  Fills/accepts fields, clicks Save
Step 4  POST /api/candidates {name, email, phone, …}
Step 5  BACKEND: requireRole(["owner","admin","recruiter"])
        parseCandidatePayload(body,"create")
          - name required
          - email pattern + lowercase
          - phone ≥6 digits
          - MUST have email OR phone
          - skills deduped/capped
          - education & employment_history NORMALISED, not rejected
            (refusing the whole save because one row is half-filled would lose
             the other six)
Step 6  findDuplicateCandidates({email, phone}) runs BEFORE the insert
Step 7  If duplicates found AND acknowledge_duplicates is not true:
          → HTTP 409 {error:"This candidate may already exist.",
                      code:"duplicate_suspected", duplicates:[…]}
          → NOTHING IS CREATED YET
Step 8  UI shows the warning banner with each suspected match and what collided
Step 9  Recruiter re-submits with acknowledge_duplicates: true
Step 10 INSERT candidates (organization_id from the SESSION)
        DB trigger trg_candidates_normalize_contact fills
        email_normalized / phone_normalized
        DB trigger trg_candidates_mark_matches_stale invalidates match scores
Step 11 Best-effort INSERT into candidate_duplicates for later review
        (a failure here does NOT undo the candidate)
Step 12 logActivity "candidate.created" (+ "candidate.duplicate_flagged")
Step 13 RESPONSE 201 {data, duplicates}
```

**A suspected duplicate never blocks creation.** The same person legitimately
re-applies, and blocking would strand a real candidate.

## 11.4 API Flow

| API | Method | Auth | Notes |
| --- | --- | --- | --- |
| `/api/candidates` | GET | any member | Filters validated by `filtersFromSearchParams()`; paginated |
| `/api/candidates` | POST | owner/admin/recruiter | **409 `duplicate_suspected`** on first pass; `acknowledge_duplicates:true` to proceed |
| `/api/candidates/[id]` | GET | any member | Returns the candidate **plus its duplicates**; 404 cross-tenant |
| `/api/candidates/[id]` | PATCH | owner/admin/recruiter | Translates the `candidates_contactable` CHECK into a readable message |
| `/api/candidates/[id]` | DELETE | **owner/admin** | **ARCHIVES**. 404 "Candidate not found, or already archived." |
| `/api/candidates/lookup` | GET | **any member** | `?q=` typeahead by name/email/phone |
| `/api/candidates/search` | POST | **any member incl. Viewer** | Two separated steps: AI parses the sentence into filters, then a **deterministic** query runs. AI never selects rows. |
| `/api/candidates/ai-action` | POST | owner/admin/recruiter | Structures a blurb; `saved:false` |

**Natural-language search is deliberately two-phase.** `parseCandidateSearch()`
turns the sentence into structured filters; the database query is then ordinary
and deterministic. That separation is what makes the results reproducible and
keeps a Viewer's search read-only.

## 11.5 Database Flow

```
USER ACTION  Save candidate
 → API       POST /api/candidates
 → BACKEND   requireRole → parse → findDuplicateCandidates → (409 or continue)
 → DATABASE  INSERT public.candidates
               CHECK candidates_contactable (email OR phone)
               CHECK total_experience_years 0..60
               CHECK notice_period_days 0..365
               trigger trg_candidates_normalize_contact
               trigger trg_candidates_touch_updated_at
               trigger trg_candidates_mark_matches_stale
             INSERT public.candidate_duplicates (best effort)
             INSERT public.activity_events
 → RESPONSE  201 {data, duplicates}
 → UI        detail page + duplicate banner if any
```

Note `candidates."current_role"` is **quoted in DDL** because `current_role` is a
reserved word in PostgreSQL. PostgREST and TypeScript refer to it unquoted.

`trg_candidates_guard_delete` (`guard_candidate_delete_with_resumes()`) blocks a
hard delete when resumes exist.

# 12. MODULE M09 — Resumes & Resume AI Parsing

## 12.1 Purpose

Turn a PDF/Word file into structured candidate fields **without ever letting the
AI overwrite trusted data**. Upload → extract → parse → review a field-by-field
diff → apply only what the recruiter accepted.

**Who uses it:** Owner/Admin/Recruiter upload, parse and review; Viewer can list
and download.

## 12.2 The enforcement point

`lib/resumes/review.ts` — `applyReviewDecisions()` accepts **explicit per-field
decisions** and returns **only** the fields the recruiter chose to accept. A field
absent from the decisions is never written, so *the default outcome of doing
nothing is that nothing changes.*

Reviewable fields (`REVIEWABLE_FIELDS`): name, email, phone, location,
current_company, current_role, total_experience_years, expected_salary,
notice_period_days, skills.

## 12.3 Upload policy (`lib/resumes/uploadPolicy.ts`)

- Allowed: **`.pdf`, `.doc`, `.docx` only**.
- Rejection message, in one place so client and server agree:
  **"Only PDF and Word documents (.doc, .docx) are supported"**
- **Extension first, MIME as fallback.** Browsers disagree about `.doc`
  (`application/msword`, `application/octet-stream`, or nothing at all), and
  rejecting a real Word document because the browser mislabelled it would be an
  unexplainable failure.
- Max **10 MB**, matching the bucket's `file_size_limit`.
- The extractor (`extract.ts`) can also read `.txt`, but the *upload* policy is
  narrower on purpose.
- `MAX_EXTRACTED_CHARACTERS = 40,000`; `MIN_USEFUL_CHARACTERS = 120` — below that
  the UI must say the file yielded almost no text (a scanned image PDF) rather
  than blaming the AI.


# 13. MODULE M10 — Applications Management

## 13.1 Purpose

An application is one candidate against one job. It is the row every later module
hangs data off: matches, screening calls, reports, evaluations, interviews,
submissions, onboarding.

**Who uses it:** Owner/Admin/Recruiter create, move and annotate; Owner/Admin
archive; Viewer reads. A **Recruiter's list shows their own plus unassigned**.

## 13.2 The stage model (`lib/applications/stages.ts`)

**Board stages, in order:**
`applied → shortlisted → ai_screening_call → phone_interview → video_interview →
written_assessment → director_round → hired`

**Terminal exits, reachable from ANY stage (not board columns):** `rejected`,
`withdrawn`.

**Phases** (derived, never stored — `lib/applications/phase.ts`):

| Phase | Stages |
| --- | --- |
| screening | applied, shortlisted, ai_screening_call |
| interviewing | phone_interview, video_interview |
| final | written_assessment, director_round |
| closed | hired, rejected, withdrawn |

**Transition rule (`canTransition`)** — deliberately permissive about
**direction**: recruiters legitimately move applications backwards. What it
forbids is **resurrecting a finished application**: from `hired`, `rejected` or
`withdrawn`, nothing is allowed, with the message *"This application is already
{stage}. Create a new application to consider this candidate again."* Reopening a
hire or rejection silently would corrupt the funnel that analytics reports on.

`DEFAULT_APPLICATION_STAGE = "applied"` is a typed constant referenced by every
creation path — because the Supabase client has no generated row types here, a
string literal that stopped being valid would keep compiling and fail at runtime
(exactly what happened when migration 0021 renamed `new` → `applied`).

`rejected_at_stage` is stamped by `trg_applications_stamp_rejected_stage` — a
candidate turned down after a director round and one turned down on their CV are
not the same outcome.

**Priority** (`low` | `normal` | `high`) is recruiter-set, **not** derived from
stage or SLA. `normal` is deliberately a neutral chip: a board where every card
wears a colour communicates nothing.

## 13.3 The candidate-field refusal (`lib/applications/validation.ts`)

`name`, `email`, `phone` (plus `email_normalized`, `phone_normalized`, `candidate`,
`candidate_name`, `candidate_email`, `candidate_phone`) are **rejected outright**
by `PATCH /api/applications/:id` with HTTP **422** and the message:

> "Candidate name, email and phone are edited on the candidate's own page, not here."

The check uses `field in payload`, so **`{"email": null}` counts** — that is an
attempt to erase an address, not an absence of intent. One candidate can hold five
applications; letting any application edit their phone number means five screens
racing to own one fact.

## 13.5 Complete User Flow — move a stage (and everything it sets off)

```
USER ACTION   Recruiter picks "Shortlisted" in the stage control
→ FRONTEND    PATCH /api/applications/{id} {stage:"shortlisted"}
→ BACKEND     requireRole(["owner","admin","recruiter"])
              rejectCandidateFields(body) → 422 if name/email/phone present
              load the current row → 404 if not this org's
              isApplicationStage(stage) → 400 "Invalid stage."
              canTransition(from,to) → 409 with the terminal-stage reason
→ DATABASE    UPDATE applications SET stage
                trigger trg_applications_stage_history
                  → closes the open application_stage_history row (exited_at)
                  → opens a new one (entered_at, changed_by)
                trigger trg_applications_stamp_rejected_stage (if → rejected)
                trigger trg_applications_create_onboarding (if → hired)
                trigger trg_applications_touch_updated_at
→ AUDIT       logActivityBatch: application.stage_changed
              (+ application.recruiter_assigned when that changed)
→ NOTIFY      notify("assigned_to_application") — ONLY when the assignee
              actually changed AND it is not the actor assigning to themselves
→ CANDIDATE   trySendForEvent(EVENT_FOR_STAGE[stage])   ← BEFORE automations
              (so the candidate hears about the stage a PERSON moved them to,
               not one an automation moved them to a second later)
              No entry for phone/video interview: those messages state a TIME,
              and a stage move has none — they fire from scheduling instead.
→ AUTOMATION  dispatch(trigger:"application_stage_changed")
              AWAITED (a serverless freeze would strand a half-run automation
              with its claim row written) but WRAPPED — a failing automation
              must never fail the manual action
→ RESPONSE    {data: application}
→ UI          router.refresh(); stepper, timeline and banner all update
```

# 14. MODULE M11 — AI Matching

## 14.1 Purpose

Score how well a candidate fits a job, split into a **deterministic** half built
from checkable facts and an optional **semantic** half from the AI — and make sure
the number and the explanation can never contradict each other.

## 14.2 How the score is built

**CODE owns the number.** The model cannot state a score at all, so it cannot
state one that disagrees with the facts beside it.

### Deterministic component weights (`COMPONENT_WEIGHTS`, overridable per job)

| Component | Weight |
| --- | --- |
| skills | 40 |
| experience | 20 |
| salary | 15 |
| location | 15 |
| notice | 10 |

**Missing data is SKIPPED, not scored zero**, and the remaining weights are
renormalised. Scoring a blank field as zero would punish an incomplete profile as
though it were a bad fit — a different and much more damaging claim.

- Skills: literal, case-insensitive overlap. Equivalence judgement is the AI's job.
- Location: loose substring either way — "Gurgaon" matches "Gurgaon, Haryana";
  genuinely different cities do not match.
- Notice thresholds: `COMFORTABLE = 30`, `ACCEPTABLE = 60`, `LONG = 90` days.

### Combination (`lib/matching/score.ts`)

`SEMANTIC_WEIGHT = 0.3`, `DETERMINISTIC_WEIGHT = 0.7` (a job may override).
The semantic minority share is deliberate: the deterministic half rests on
recorded facts, the semantic half on judgement.

Semantic score = `roleSimilarity*0.6 + seniorityFit*0.4`, lifted by confident
skill equivalences (capped at 1 — the model cannot claim to cover more skills
than were missing).

**When AI is unavailable**, `semantic` is `null`, the deterministic score **is**
the overall score, and `ai_used = false` so the UI says so rather than implying a
semantic read happened.

### The three labelled lists
`strong_matches`, `gaps`, `needs_verification` — each entry records whether it was
**checked by code** or **assessed by AI**, so a recruiter can tell a fact from a
judgement.

## 14.3 Staleness

`application_matches.is_stale` is set by database triggers — **not** recalculated
on every page view (the cost model forbids that):

- `trg_candidates_mark_matches_stale` — the candidate's profile changed
- `trg_jobs_mark_matches_stale` — the job's requirements changed

`trg_matches_sync_application_score` keeps `applications.match_score` in step.

`UNIQUE (application_id)` — one current match per application; recalculation replaces it.

## 14.4 UI + API Flow

`/applications/[id]/match` → `MatchView`.

| API | Method | Auth | Behaviour |
| --- | --- | --- | --- |
| `/api/applications/[id]/match` | GET | any member | Calculates on demand when absent or stale — **but a Viewer never triggers a calculation**; they see what exists. Returns `{data, calculated}` |
| `/api/applications/[id]/match` | POST | owner/admin/recruiter | Forces a recalculation. 404 when "not found" appears in the error, else 400 |

# 15. MODULE M12 — AI Screening Calls (Bolna)

## 15.1 Purpose

Place an automated outbound voice call to a candidate, ask the job's screening
questions, and bring back a transcript. **Everything a real person hears is
regulated**, so this module is designed to fail closed at every step.

**Who uses it:** Owner/Admin/Recruiter trigger; Viewer reads. A Viewer must
**never** be able to make the product telephone someone.

## 15.2 The consent disclosure — non-negotiable

`buildCallScript()` **always** emits the consent disclosure as the **first
segment**. There is no parameter to disable it, and a unit test asserts it cannot
be removed. It states three things: who is calling, that the call is automated,
and that it may be recorded — then makes continuing an explicit, informed choice.

Segment kinds, in order: `consent` → `greeting` → `briefing` → `question`… → `closing`.

The job's stage prompt lands as a **`briefing`, after consent and after the
greeting**. It **supplements** the script; it can never replace or precede the
disclosure. A recruiter-authored prompt that could displace it would be a
compliance hole with a text box in front of it.

Caps: `MAX_QUESTIONS = 12` (beyond that a call stops being a screen),
`MAX_INSTRUCTIONS_LENGTH = 2000` (so one job cannot turn a screen into a monologue).

**Recording someone without telling them is unlawful in many jurisdictions.**
Treat any failure here as **Critical**, not cosmetic.

## 15.3 Retry policy (`lib/screening/retry.ts`)

| Setting | Default | Bound |
| --- | --- | --- |
| `maxAttempts` | **3** | `MAX_ALLOWED_ATTEMPTS = 5` |
| `delayMinutes` | **120** | `MIN_ALLOWED_DELAY_MINUTES = 15` |

**Retryable:** `no_answer`, `busy`, `failed`.
**Terminal (never auto-retried):** `completed`, `answered`, `cancelled`,
**`callback_requested`**.

`callback_requested` is the important one: the candidate asked to be called at a
different time. Dialling them again on our schedule ignores what they said. A
human decides when.

The attempt cap does double duty — a **cost cap** (the Bolna call is the highest
single-event cost) and **decency** (three unanswered calls is persistence; ten is
harassment, and a runaway automation that dialled someone repeatedly would be a
serious harm).

## 15.4 UI Components

| UI Component | Location | Purpose |
| --- | --- | --- |
| **AI screening call** card | `/applications/[id]` | Status, attempts |
| **Start a call** button | `/applications/[id]/screening-call` (`StartCallPanel`) | Explicit human trigger |
| "What the candidate hears first" | same | **Shows the consent disclosure before you dial** |
| "Attempts" counter | same | Against the configured cap |
| "Call transcript" | same | After the webhook lands |
| `/screening-calls` list | global | All calls with `CallStatusBadge` |

## 15.5 Complete User Flow

```
Step 1  Recruiter opens /applications/{id}/screening-call
Step 2  The panel SHOWS the consent disclosure text ("What the candidate hears
        first") before any dialling is possible
Step 3  Recruiter clicks Start a call
Step 4  POST /api/applications/{id}/screening-call
        requireRole(["owner","admin","recruiter"])   ← Viewer can never dial
Step 5  startScreeningCall():
          - Bolna integration must be CONNECTED (fails closed if not)
          - retry policy read from organization_settings.screening_settings
          - attempt cap enforced
          - buildCallScript() with the job's questions + rendered stage prompt
          - the provider is called with a metadata.screening_call_id = OUR id
Step 6  DATABASE INSERT screening_calls
          status 'queued', attempt_number, triggered_by,
          consent_confirmed FALSE
          trigger trg_screening_calls_consent (stamp_screening_consent)
          trigger trg_screening_calls_tenant_integrity
Step 7  RESPONSE 201 {data:{id}}
...call happens...
Step 8  Bolna POSTs /api/webhooks/bolna
          NO SESSION. Three constraints:
            1. HMAC-SHA256 over the RAW BYTES, constant-time compare.
               No BOLNA_WEBHOOK_SECRET → 503, every request rejected.
               Bad/missing signature → 401 (deliberately vague).
            2. TENANCY COMES FROM OUR ROW. screening_calls is looked up by the
               id WE generated; organization_id is read from that row.
               A forged organization_id in the payload is IGNORED.
            3. It can only advance ONE KNOWN CALL. It cannot create rows and
               cannot touch anything outside screening_calls.
          Unknown call id → 200 {received:true, matched:false}
            (200 so the provider stops retrying an event we will never accept)
          Update failure → 500 so the provider RETRIES
            (losing a transcript silently is worse)
Step 9  Recorded: status, ended_at, transcript, recording_url,
        duration_seconds, failure_reason (truncated to 500 chars)
        consent_confirmed set ONLY if the candidate heard the disclosure and
        did not decline (isConsentRefusal())
Step 10 Notification + activity event; automations on `screening_call_completed`
        (a SERVICE-mode trigger, since there is no session)
```

# 16. MODULE M13 — AI Screening Report

## 16.1 Purpose

Turn a call transcript into structured facts a recruiter can act on — interest
level, expected CTC, notice period, location acceptance, availability — while
keeping **what the AI originally said** permanently distinguishable from **what a
human corrected**.

## 16.2 The two rules that define this module

### 1. Eligibility — consent is checked FIRST

`checkReportEligibility(call)` refuses in three ways:

| Code | When | Message |
| --- | --- | --- |
| `no_consent` | `consent_confirmed = false` | "No consent was recorded on this call, so its transcript can't be used. The candidate must be told the call is recorded and agree to continue." |
| `not_completed` | the call did not complete | — |
| `no_transcript` | no transcript text | — |

Consent is checked **before** anything else, deliberately: without confirmation the
recording is not ours to process, regardless of how good the transcript is. The
database enforces the same rule via `trg_screening_reports_preconditions`
(`enforce_screening_report_preconditions()`), so this is the friendly-message half.

### 2. The AI's original words are frozen forever

`screening_reports` carries **two parallel sets** of columns:

| Current (editable) | Original AI (never updated after insert) |
| --- | --- |
| `summary_text` | `ai_summary_text` |
| `interest_level` | `ai_interest_level` |
| `expected_ctc` | `ai_expected_ctc` |
| `notice_period_days` | `ai_notice_period_days` |
| `location_accepted` | `ai_location_accepted` |
| `availability_notes` | `ai_availability_notes` |

Plus `uncertain_fields[]` (fields the model itself flagged, surfaced so a
recruiter checks them first) and `corrected_fields[]` (fields a human changed).

`trg_screening_reports_protect_ai` (`protect_ai_screening_original()`) **refuses
any update to an `ai_*` column**. The API translates that into
*"The original AI extraction cannot be edited."*

`UNIQUE (screening_call_id)` — one report per call; regenerating replaces it.

## 16.3 UI Components

`/applications/[id]/screening-report` → `ReportEditor` (316 lines).
Cards on the application detail page: "Screening report", "No report yet",
"What the candidate said", **Regenerate**.

## 16.4 Complete User Flow

```
Step 1  A call completes with consent and a transcript
Step 2  Recruiter opens /applications/{id}/screening-report
Step 3  Clicks Generate (or Regenerate)
Step 4  POST /api/applications/{id}/screening-report
        requireRole(["owner","admin","recruiter"])
          — generating costs an AI call, so a Viewer cannot spend it
Step 5  checkReportEligibility(latest completed call)
        → refuses with a code + reason if consent/completion/transcript missing
Step 6  generateScreeningSummary() → schema-validated extraction
Step 7  INSERT screening_reports with BOTH the current values and the frozen ai_*
        copies, plus uncertain_fields[]
Step 8  RESPONSE 201 {data:{id}}
Step 9  Recruiter reads the report; uncertain fields are highlighted first
Step 10 Recruiter corrects a value, clicks Save
Step 11 POST /api/screening-reports/{id}/review
        - updates only the CURRENT columns
        - records the field in corrected_fields[]
        - sets reviewed_by / reviewed_at
        - ANY attempt to write an ai_* column → 400
          "The original AI extraction cannot be edited."
Step 12 The report now shows: what the AI said, what a human changed, and by whom
```

| --- | --- | --- | --- |

# 17. MODULE M14 — Structured Evaluations & Next Action

## 17.1 Purpose

One uniform view of *how the candidate did* at every judged stage, merged from
four different underlying sources, plus a **suggested** next step that a human
must click.

## 17.2 The read model — five sections, four sources

| Section | Source(s) |
| --- | --- |
| AI Screening Call | `screening_calls` + `screening_reports` (M12/M13) |
| Phone Interview | `interviews` (mode `phone`) + `interview_feedback` **and** `application_evaluations` (for calls held off-system) |
| Video Interview | `interviews` (mode `video`) + `interview_feedback` **and** `application_evaluations` |
| Written Assessment | `application_evaluations` only |
| Director Round | `application_evaluations` only |

**Merging, not copying, is the whole point.** A second log would be invisible to
the screening-report screen and the interview scheduler, so a call recorded in one
place would be missing from the other.

**Scores are scaled to 1–10 for display.** `interview_feedback` stores **1–5**,
`application_evaluations` stores **1–10**, and screening reports had no score at
all until migration 0022. One column of badges must mean one thing, so the scale
is normalised for display and the native value is kept alongside.

`MANUAL_EVALUATION_STAGES` (stages that accept a manually logged entry):
`phone_interview`, `video_interview`, `written_assessment`, `director_round`.
**`ai_screening_call` is not manually loggable** — it comes from the call.

## 17.3 Verdict and thresholds (`lib/evaluation/verdict.ts`)

`EVALUATION_STATUSES = pass | fail | needs_review`, with tones
success / error / **warning**. `ROUND_SCORE_MAX = 10`, `RESUME_SCORE_MAX = 100`.
`MAX_LIST_ITEMS = 4` highlights.

## 17.4 Next Action (`lib/evaluation/nextAction.ts`) — a suggestion, never an act

> Nothing here moves a stage, rejects anyone, or writes a row. It renders as a
> labelled chip with a button the recruiter must click, and clicking goes through
> the same confirmation the move-to-stage control already uses.

| Kind | When | Behaviour |
| --- | --- | --- |
| `stop` | the last round failed | suggests ending it |
| `proceed` | passed, and the job has a further stage | target = the next stage in the **effective** list |
| `hire` | passed the last configured round | suggests Hired |
| `awaiting` | nothing judged yet | no button |
| `none` | already hired/rejected/withdrawn | no button |

`visibleStages` is the application's **effective** stage list
(`lib/applications/effectiveStages.ts`), so a job that switched Video Interview
off never gets "Proceed to Video Interview" suggested.

## 17.5 UI Components

`EvaluationPanel` (375 lines) + `EvaluationEntryForm` on `/applications/[id]`;
`EvaluationVerdict` and `NextActionBanner` components.
Fields: **Score (1-10)**, **Outcome** (pass/fail/pending), **Summary**
(placeholder "What happened, and what you concluded."), occurrence date.

## 17.6 API Flow

| API | Method | Auth | Errors |
| --- | --- | --- | --- |
| `/api/applications/[id]/evaluations` | POST | owner/admin/recruiter | 400 validation; 404 application; **refused for a stage this application's job does not have**; 400 "Could not save this entry." |
| `/api/applications/[id]/evaluations/[entryId]` | PATCH | owner/admin/recruiter | Only rows in `application_evaluations` are editable — **a screening report or interview feedback is not**; 404 "That entry could not be found." |

## 17.7 Database Flow

`application_evaluations (id, organization_id, application_id,
stage_key CHECK IN ('phone_interview','video_interview','written_assessment','director_round'),

`occurred_at` is **when the thing happened**, which is not when it was logged — a
recruiter writing up Friday's call on Monday needs the list ordered by the call.

Triggers: `trg_application_evaluations_tenant`, `trg_application_evaluations_touch`.

An `evaluations_complete` automation trigger fires when the last outstanding

# 18. MODULE M15 — Pipeline Board & SLA

## 18.1 Purpose

The Kanban view of every active application, coloured by how long each has been
sitting still. Answers "where is everyone, and who is stuck?".

**Who uses it:** Owner/Admin/Recruiter can move cards and ask the pipeline AI;
Owner/Admin can edit SLA targets; Viewer reads. A **Recruiter sees their own plus
unassigned**.

## 18.2 Design decisions the tester should know

- **Buttons/dropdowns, not drag-and-drop.** Deliberate: a dropdown is
  keyboard-accessible, works on a phone, and cannot fire from a mis-drag. Moving
  someone through a hiring pipeline should be deliberate.
- **Terminal outcomes are exit counts, not columns.** Otherwise the board fills
  with finished work and stops being a work queue.
- **SLA accent is a left rule**, not a filled background — readable, and it keeps
  the flat card style.

## 18.3 SLA model (`lib/pipeline/sla.ts`)

Default target days per stage:

| Stage | Default target |
| --- | --- |
| applied | 2 |
| shortlisted | 3 |
| ai_screening_call | 3 |
| phone_interview | 5 |
| video_interview | 7 |
| written_assessment | 7 |
| director_round | 7 |
| hired / rejected / withdrawn | not tracked |

`AT_RISK_THRESHOLD = 0.75` — "at risk" once 75% of the target has elapsed.

Statuses: `ok` | `at_risk` | `breached` | `not_tracked`.

**An absent `pipeline_sla_config` row means "use the default", never "no SLA"** —
a board with no aging at all would defeat the point of the module. Terminal stages
return `not_tracked`: showing a hired candidate as "12 days overdue" would be
noise that trains people to ignore the indicator.

## 18.5 Complete User Flow

```
Step 1  Recruiter opens /pipeline
Step 2  getBoard({organizationId, viewerRole, viewerId, jobId})
        - RLS + role scoping (recruiter → own + unassigned)
        - per-card SLA assessed from days-in-stage vs the configured target
Step 3  Board renders; overdue cards carry a coloured left rule
Step 4  Recruiter picks "Move to…" → Shortlisted on a card
Step 5  PATCH /api/applications/{id} {stage}
        (the SAME endpoint the detail page uses — one rule, one code path)
Step 6  Everything in §13.5 happens: history, audit, notify, candidate message,
        automations
Step 7  router.refresh(); the card moves columns
```

## 18.8 Known Risks — M15

1. **Only the first 12 jobs** get a filter button. On a larger org the rest are
   unreachable from this page.
2. A card move is a full page refresh; on a big board that is a visible pause.
3. `AT_RISK_THRESHOLD` is a fraction of the target, so a 2-day target flips to
   at-risk after 1.5 days — check that reads sensibly for short stages.
